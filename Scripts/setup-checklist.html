Zeitkonto · setup runbook

Everything left that only you can do

The app is written, tested and green. What remains is the part a repository cannot reach: things that need an Apple account with your name on it, a bank account, and a card.

In order, because the order matters — two of these steps fail silently and confusingly if you do them in the wrong sequence. Tick as you go; the page remembers.

0 of 0 done

You need none of this to use the app yourself today

Clone the repository, open Hours.xcodeproj, press ⌘R. It runs in the simulator with no Apple account, no signing and no network. Everything below is about getting it off the simulator.

Phase 1 — free

Put it on your own iPhone

A free Apple ID is enough. You get the app on your phone; you do not get widgets, iCloud sync, or the ability to sell it.

  1. Free5 minutes

    developer.apple.com › Certificates, Identifiers & Profiles › Identifiers

    These are already set in the project, derived from the domain you own, so there is nothing to invent. What is left is telling Apple they exist: register the app identifier and the widget's, because an unregistered widget identifier is why a widget silently fails to install. The other two are test targets and never leave your machine.

    • App
    • Widget
    • Unit tests
    • UI tests

    If you change this, come back and change the three product identifiers in step 17 to match — they are prefixed with it.

  2. Free2 minutes

    Xcode › Hours target › Signing & Capabilities › Team

    The project deliberately ships with no DEVELOPMENT_TEAM set, so it does not carry someone else's account around. Choose your Apple ID from the dropdown and leave Automatically manage signing ticked. Do it for the HoursWidgetExtension target too.

  3. Free2 minutes

    iPhone › Settings › General › VPN & Device Management

    The first build onto a device installs but refuses to open, with an unhelpful message. Tap your developer certificate there and trust it. Once, per device.

    Free-account limit

    An app signed with a free Apple ID stops working after seven days and has to be rebuilt from Xcode. That is Apple's rule, not something in the code. It is the main reason to go to Phase 2 even if you never sell anything.

Phase 2 — the domain

Point zeitkonto.app at the site

Nothing here involves Apple. Do it early anyway: DNS takes time to spread and the certificate takes longer, and the privacy policy and support URLs have to resolve before a submission is accepted. The site itself is built and committed in docs/ — this deploys it with Cloudflare Pages and connects the name to it.

  1. 15 minutesFree

    dash.cloudflare.com › Add a domain

    Enter zeitkonto.app, choose the Free plan, and let Cloudflare import the existing records. It then names two nameservers. At your registrar, replace the domain’s nameservers with those two; the registration itself stays where it is. Cloudflare emails when the domain is active — usually within the hour, sometimes a day.

    Cloudflare serving the DNS is what lets the bare zeitkonto.app point at the site at all: the apex cannot take an ordinary CNAME, and Cloudflare flattens one for you.

  2. 10 minutesFree

    dash.cloudflare.com › Workers & Pages › Create › Pages › Connect to Git

    Authorise Cloudflare on GitHub for this repository only, pick it, and set:

    • Production branch
    • Framework preset
    • Build command leave empty
    • Build output directory

    Save and Deploy. Nothing is built: docs/ is the site, already built and committed, and CI checks it against web/ on every push — so what Cloudflare serves and what the repository says is live are the same files. Every push to main redeploys.

    Open the …pages.dev address it gives you and check /, /de/, /privacy/ and /support/ there before attaching the domain.

    Then the project › Custom domains › Set up a custom domain › zeitkonto.app. With the domain already on Cloudflare it adds the record and the certificate itself. Add www.zeitkonto.app the same way if you want it.

  3. 1 minuteBlocks the listing

    Any browser

    • English
    • German
    • Policy
    • Support

    .app is HTTPS-only, and this is where it bites. The whole .app top-level domain is on the browser preload list, so browsers refuse to speak plain HTTP to it — there is no insecure version to land on. Between the DNS resolving and the certificate being issued, the site is not slow or ugly, it is unreachable. That is normal, it is usually minutes, and the thing to do about it is wait rather than start changing settings.

    There is a script for exactly this: python3 Scripts/check-site-routes.py https://zeitkonto.app checks the pages, the images and the redirects. Cloudflare answers the working notes in docs/ with a redirect to the home page (_redirects) where Caddy answers 404, so expect the script to report those three lines differently against Cloudflare.

    Nothing public links to the repository and Cloudflare deploys from a private one, so the repository can be made private without touching the site.

Phase 3 — $99 a year

Join the Developer Program

This is what unlocks the two features the code already contains but cannot switch on: the widgets and iCloud sync. Both are written, both are dormant, and both need a paid account for reasons that are Apple's, not the app's.

  1. $99 / yearBlocks 8–241–2 days to be approved

    developer.apple.com/programs

    Nothing below this line is possible without it. Approval usually takes a day or two and occasionally asks for identity documents, so start it before you need it rather than on the evening you want to ship.

    Individual or Organization — decide before you pay. An individual enrolment needs no company and no D-U-N-S number, and can take money perfectly well. What it does is put your own legal name on the App Store as the seller. An Organization enrolment shows the company name instead, and needs a real legal entity plus a D-U-N-S number, which is free but takes its own few days. Moving from one to the other afterwards is a migration, not a setting, so this is worth ten minutes now.

  2. Needs step 75 minutesTurns on widgets

    developer.apple.com › Certificates, Identifiers & Profiles › Identifiers

    A widget runs in its own process and cannot open the app's database, so the app writes a small snapshot into a shared container and the widget reads that. The container is the App Group. The app and the widget already ask for it in their entitlements; Apple only grants it once the group exists in your account. Click + › App Groups and register:

    • Group

    Then open the identifier app.zeitkonto.hours, tick App Groups, configure it, tick the group and save. Do the same for app.zeitkonto.hours.widget. The TestFlight workflow checks this before it builds and makes new signing profiles on its own afterwards. Until it is done the widgets say so on their face rather than showing a convincing screenful of zeroes.

  3. Needs step 710 minutesTurns on sync

    Signing & Capabilities › + Capability › iCloud

    Tick CloudKit and Key-value storage, then create the container. Days and holidays travel through CloudKit; your settings travel through key-value storage, because a second device computing expected hours from a different contracted week would produce wrong figures rather than merely different ones.

    • Container

    Already in the code at SyncPreference.containerIdentifier. If the switch is on but the entitlement is missing, the app quietly opens its local store and tells you — it never refuses to start. The switch itself takes effect at the next launch, because a store's iCloud setting is fixed at the moment it opens.

  4. Decision, not a task

    A day you delete is deleted on every device. The backup file in Settings › Backup and data is the only copy that survives losing the phone — plain readable JSON with every day, every holiday and all your settings. Write one somewhere before you trust the app with a year of hours.

Phase 4 — testing

Put it on a device with TestFlight

This is how you use the app on an iPad without a cable, and how anyone else tries it before it is on sale. Three separate Apple things are involved and confusing them is most of the difficulty: developer.apple.com is where identifiers and certificates live, App Store Connect is where the app record, the builds and TestFlight live, and Xcode is what makes a build and sends it. You never upload a file to a website by hand.

  1. 5 minutesBlocks everything below

    appstoreconnect.apple.com › Apps › +

    This is where the name is claimed. App Store names are unique across the whole store, so if Zeitkonto is taken you find out here, and it is worth doing before anything else is printed with it on. Pick the bundle identifier you registered in the previous phase from the list — if it is not there, it was never registered.

  2. 10 minutesNeeds a Mac

    Xcode › Product › Destination › Any iOS Device, then Product › Archive

    Archiving builds a signed, installable version — which is why it cannot be done on a simulator, and why the destination has to be a device. When it finishes, the Organizer window opens: Distribute App › TestFlight & App Store. That sends it straight to App Store Connect. There is no file to save and no page to drag it onto.

    Expect a few minutes of processing after the upload, and an email if it is rejected for something mechanical — a missing icon size, a privacy string.

  3. 2 minutesThen it is on the iPad

    App Store Connect › your app › TestFlight › Internal Testing

    Internal testers are people on your own team, up to 100, and their builds need no review — the build is available within minutes. External testers, up to 10,000 by email or public link, need a short beta review for the first build of each version, usually a day.

    Then on the iPad: install TestFlight from the App Store, sign in with the same Apple Account, accept the invitation, and the app is there. Every later build you upload appears in the same place, so this is the last time you touch a cable.

    A TestFlight build stops working 90 days after upload. That is an expiry on the build, not on anything you have done wrong.

Phase 5 — only if you sell it

Switch on Zeitkonto Pro

Skip this entirely if the app is just for you — everything works unpaid in a build you sign yourself. The order in this phase is not a suggestion: step 14 done before step 17 wastes an afternoon.

  1. Do this firstDays, if the bank details bounce

    App Store Connect › Business › Agreements, Tax, and Banking

    The expensive mistake

    Until this agreement is signed and your bank and tax details are accepted, StoreKit returns zero products and no error. The paywall renders empty, the app looks broken, and nothing anywhere tells you why. People lose a day to this.

    Sign it before you create the products, not after.

  2. 15 minutesHalves the commission

    App Store Connect › Business › Agreements, Tax, and Banking

    Apple's commission is 30%. Under the Small Business Program it is 15%, for anyone who earned under one million dollars across all their apps in the previous year — which is almost certainly you.

    It is not automatic. You apply, and it takes effect the month after you are accepted; nothing backdates. Fifteen per cent of everything the app ever earns is a large sum to leave behind because a form went unfilled.

  3. Blocks EU distributionThink before filling it in

    App Store Connect › Business › Trader status

    Selling in the EU requires a trader declaration under the Digital Services Act: name, address, phone number and email. Without it the app cannot be distributed in the EU at all.

    Those details are shown publicly on your App Store page. Not merely held by Apple — displayed, beside the app, to anyone who looks. Enrol as an individual working from home and that is your home address on a public page.

    This, rather than anything on Apple's enrolment form, is the real argument for a company: a registered business address keeps your home address off it. A mail-forwarding address only works if it is legally valid as a business address where you live, which is worth checking before you rely on it.

    Apple changes this area regularly and it interacts with how you are registered locally. Worth an hour with an accountant before you fill it in, not after.

  4. Done by a workflow5 minutes

    GitHub › Actions › App Store › Run workflow › what: products

    The workflow creates the subscription group (reference name Hours Pro, shown to customers as Zeitkonto Pro), the monthly and yearly subscriptions in it, and the lifetime purchase, with names and descriptions in English and German and the prices set. Whatever exists is skipped, and the log lists what it made. The identifiers match SubscriptionStore.ProductID exactly:

    • Monthly
    • Yearly
    • Lifetime

    The API key needs the Admin or App Manager role. If Apple refuses, the run says what to create by hand instead. Still by hand either way: a review screenshot of the paywall on each product’s page.

  5. Decided

    €2.99 a month, €19.99 a year, €39.99 outright, set in Germany; Apple works out every other territory from it. The numbers in HoursTests/Hours.storekit are only for the simulator.

    Worth remembering what is and is not behind the payment: recording hours is free forever, and nothing already recorded is ever withheld — if a subscription lapses every figure is still there and the backup still writes. What is paid for is producing and creating: the exports, the widgets and the Live Activity, more than one site, a second job, and editing a range in one pass.

  6. Easy to miss1 minute

    Product › Scheme › Edit Scheme › Run › Options › StoreKit Configuration → None

    The Hours scheme currently points Run and Test at HoursTests/Hours.storekit, which is what lets you exercise buying, cancelling, expiring and refunding in the simulator with no account and no network. It is genuinely useful — right up to the moment you want to test a real sandbox purchase.

    While that file is selected, Xcode serves it instead of talking to App Store Connect. A product you have configured perfectly will still look missing. Set it to None when you want the real thing, and put it back afterwards.

Phase 6 — submission

The listing itself

The part that is writing rather than configuration. Two of these will get the build rejected if they are missing.

  1. Rejected without itDesigned icon is in place

    Hours/Resources/Assets.xcassets/AppIcon.appiconset/

    There was no icon at all — the asset catalogue declared a 1024×1024 slot and held no image, which App Store Connect refuses at upload. There is now a designed one: a navy hard hat on a warm amber field — the job site, where the hours are worked.

    It is drawn by Scripts/make-app-icon.py rather than committed as an opaque binary, so the geometry and the colours are editable numbers at the top of the file. Run it again after changing them. It replaced the first placeholder (four timesheet rules) and then a clock design that looked too generic.

    If you replace it by hand: 1024×1024, no alpha channel (iOS rejects transparency in an icon), square — the system applies its own rounded mask.

  2. Done for you5 minutes

    GitHub › Actions › App Store › Run workflow › what: listing

    First run Actions › Build and test › Run workflow on main. It takes seven screenshots with a sample month — a site with a crew of five, a pay rate — on the largest iPhone and on a 13-inch iPad, in English and German, and lays them out under app-store/ on the screenshots branch.

    Then the App Store workflow uploads them with the text in fastlane/metadata/, the age rating and the categories. It submits nothing. The app runs on iPad, so App Store Connect needs the iPad set as well; the run warns if it is missing.

  3. Rejected without itWritten for you10 minutes

    docs/privacy/, docs/support/ (each with a de/ page)

    Every App Store listing needs a privacy policy URL and a support URL that resolve. Both pages are written, in English and German, and are live once phase 2 is done:

    • Policy
    • Support

    Both pages give the contact address marijomiksa@pm.me, once on each of the four pages (two per language).

  4. Ten minutes of ticking "No"

    App Store Connect › App Privacy

    Data Not Collected, in every category. This is the easiest form you will ever fill in, and it is worth being able to answer it honestly — most apps cannot.

  5. Written for you10 minutes

    App Store Connect › your app

    The text is in fastlane/metadata/ (explained in notes/app-store-listing.md) and the workflow uploads it. What it deliberately does not: the App Review contact — name, phone, email — under App Review Information, and the owner’s name in fastlane/metadata/copyright.txt.

    The review notes say the app is fully functional unpaid, where the paywall is, and that the TestFlight unlock is compiled out of the review build — so submit a build made with Unlock Pro for testers off, and add the three products to the version.

Phase 7 — housekeeping

Small things I could not do from here

Each of these needs an account I do not have access to.

  1. DecisionCosts money if you say yes

    GitHub bills macOS runner minutes at ten times the Linux rate, and the simulator job needs macOS. Phase 8 — only if you want it

Genuinely optional

Nothing here blocks anything. Listed so you know it exists rather than discovering it later.

  1. Half a day per language

    The app is English only. The string catalogues are wired up and working — nineteen keys across the app and the widget — so adding a language is mostly translation rather than plumbing.

    Two strings would need moving into a catalogue first: the reminder notification's fallback body in ReminderScheduler, and the gap message built in GapFinder.message. Both are literal English inside the engine, which imports nothing but Foundation on purpose.

  2. A few minutes

    GitHub › Settings › General › Danger Zone › Change visibility

    The app is not open source, and nothing public links here any more: the site, the listing and the support page point at zeitkonto.app. Cloudflare Pages keeps deploying from a private repository, so the privacy and support URLs are unaffected.

    One cost to know first: Actions minutes on a private repository come out of the account’s monthly allowance, and macOS minutes count ten times. The simulator job and the TestFlight and App Store workflows are macOS; the budget in step 25 is what keeps that from surprising you.

If you only do one phase, do the first. Three steps, no money, and the app is on your phone this afternoon. Everything after that is about other people being able to use it.

The two steps worth reading twice before you start are 8 and 11 — both fail by showing you an empty paywall with no error, and both are ten seconds to fix once you know.
